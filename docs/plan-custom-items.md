# Партия «Сюжетные предметы» (custom items) — план

Папа-кабан, 2026-10-07, ред. 2 (по ответам проектировщика). BACKLOG п. 17 + п. 22 (п. 1, предметы с тел врагов).
Код не меняется до аппрува. Живые `saves/` только читать.

**Задача:** мастер создаёт и выдаёт сюжетные предметы (ключ, записка, перстень): название, описание, вес, цена,
флаг «квестовый»; хранятся в сейве мира, видны в /inv, «Получено», контексте мастера; забираются `take_item`.
Магические свойства/механика — вне объёма.

## 1. Ключевое решение: хранение и доступ (В1)
**Рек.: каталог мира + наложение на реестр.**
- `state/world.py`: новая модель `CustomItem(extra=forbid)`: `id, name, description="", weight_lb: float|None=None,
  cost_cp: int=0, quest: bool=False, created_s: int` (время мира) ; `WorldState.custom_items: dict[str, CustomItem]`
  (валидатор ключ==id, добавить в `check_keys`), `WorldState.custom_item_seq: int = 0`.
- Почему мир, а не герой: предмет переживает смену героя (наследник, п. 20 «живые NPC», будущие «предметы локации»
  из п. 22), инвентарь остаётся единым списком id — ни одна существующая функция инвентаря не меняется.
- Новый модуль `content/overlay.py` (или `rules/custom_items.py`): `world_registry(base, world)` →
  `base.with_items({"item": [as_item(c) for c in world.custom_items.values()]})`, где `as_item` строит
  `Item(id, name, description, cost_cp, category="valuable", source="world")`. Кэш по `(id(base),
  frozenset(custom_items))` — предметы неизменяемы после создания.
- Точки входа берут наложенный реестр вместо базового:
  `TurnRunner` — `registry` становится свойством `world_registry(self.base_registry, self.bundle.world)`
  (все вызовы `self.registry` в `game/turn.py`, `combat_flow.*` получают его автоматически);
  `GameApp.registry` — тоже свойство через runner; UI (`ui/tui/widgets.py`, `ui/tui/blocks.py`, `ui/screen.py`)
  уже ходят через `game.registry`/`app.registry`.
  Внутри хода: обработчик создания после добавления в `work.world` делает `ctx.registry = world_registry(...)`,
  чтобы следующий запрос того же хода (take_item, триггеры) видел предмет.
- Итог: /inv, «Получено», pick_valuables, триггеры, `take_item`, повторный `give_item` по id работают без правок.
- Альтернатива (отклонена): `find_item(registry, id, world)` во всех ~35 местах — шире дифф, легко пропустить место.
- Защитный фолбэк: `inv_lines`/`gains_lines` уже показывают id при `None`; `pick_valuables` пропускать неизвестный id
  вместо исключения (страховка от сирот).

## 2. Протокол (В2)
**Рек.: один инструмент `give_custom_item`** (создать + выдать), а не create/give двумя запросами:
- `GiveCustomItem(Request)`: `name` (≤ `[custom_items].name_max`=40), `description` (≤200), `qty=1`,
  `weight_lb: float|None`, `cost_cp: int=0`, `quest: bool=False`; NEUTRAL для опциональных.
- Обработчик `protocol/handlers/resources.py::give_custom_item`:
  1. валидация (пустое/длинное имя → Invalid `bad_name`; qty<1 → `bad_amount`; cost_cp<0, weight<0 → Invalid);
  2. **совпадение с SRD**: если `name` casefold совпадает с названием предмета реестра SRD → `rejected`
     «есть в реестре: give_item <id>» (не плодить «Верёвку» дублем);
  3. **дедуп**: уже есть кастомный с тем же name (casefold, trim) → переиспользовать id (ключ вернули/второй ключ);
  4. иначе id = `custom_<seq>` (seq++ в мире; детерминированно, без транслита);
  5. клэмпы: `qty ≤ give_item_max_qty`; `cost_cp ≤ [custom_items].cost_cap_cp` (рек. по уровню: таблица
     `{1-4: 5000, 5+: 50000}` cp, клэмп с сообщением, как rarity cap); лимит новых предметов за сцену
     `[custom_items].per_scene = 5` (решение В6) (счётчик `SceneState.custom_created`, по образцу `consumables_given`);
  6. `add_item`; log «Получен предмет: <name> ×qty»; result `{item_id, qty, created: bool}`.
- `give_item`/`take_item`: работают через наложение. `take_item` квестового: `why=spent` → reject? (В4).
- `protocol/apply.py`, `protocol/schema.py` (перечень), `protocol/hints.py::item_ids` — без изменений (overlay).
- Конфиг: `config/defaults.toml` `[custom_items]` + `config/settings.py` модель.

## 3. Показ
- `/inv` (`game/sheet_text.py::inv_lines`): кастомные — группа «Ценности и прочее» (category valuable); квестовые —
  **отдельная группа «Сюжетное»** первой (рек.): `inv_group` получает признак quest — через `Item.source=="world"`
  нельзя отличить quest; рек. передать в `as_item` `category="quest"` — расширить Literal `Item.category` на `"quest"`
  (контент-модель, не сейв) и `INV_GROUPS`/`CATEGORY_GROUP`. Описание — строкой под предметом (как effect_texts),
  вес/цена — если заданы («0,1 фнт, 5 зм»).
- «Получено» (`ui/screen.py::gains_lines`) — уже по имени через реестр, правок нет (тест обязателен, TUI и simple).
- `game/commands.py` — проверить команды, перечисляющие предметы (equip кастомного → `InventoryError` «нельзя надеть»
  уже есть по kind=item? проверить ветку `else`).

## 4. Контекст мастера и правила
- `master/prompt.py`: `inventory` → `[{item_id, qty, name}]` для всех; для кастомных + `description` (обрезка 120),
  `quest: true`. `item_ids` оставить из реестра SRD (`base` без кастомных? — рек. **с** кастомными: их id нужны для
  take_item; но список SRD длинный — кастомные id и так в inventory; рек. item_ids = только SRD, чтобы не раздувать).
  Для этого `ctx.base_registry` или фильтр `source != "world"`.
- `narrator_rules.md` (рядом со стр. 62): «Сюжетная вещь, которой нет в `item_ids` (ключ, письмо, перстень, карта) —
  `give_custom_item` с коротким названием и описанием, `quest: true` если важна для сюжета. Вещь из `item_ids` —
  только `give_item`. Повторно выдать/забрать — по id из инвентаря героя (`give_item`/`take_item`). Не выдумывай
  свойств: сюжетные предметы механики не имеют». Добавить тип в стр. 89 (перечень разрешённых id).
- Схема инструментов — генерится из `requests.py` (проверить `protocol/schema.py`, golden-тесты `tests/golden`).

## 5. Квестовые предметы и поражение: держатель предмета (В3, изменено)
Принцип: квестовый предмет может уйти от героя, но **не исчезает из мира** — каталог `world.custom_items` знает, где он.
Вернуть его — саб-квест (победа над держателем, переговоры, обыск тайника).

**Модель (минимальная, в сейве мира):** поле в `CustomItem` (не отдельная коллекция — один источник правды):
`holder: ItemHolder | None = None` (None — предмет у героя/в обороте, не отслеживается),
`ItemHolder(extra=forbid)`: `kind: Literal["npc", "band", "faction", "location"]`, `ref: str` (id NPC/фракции/локации;
для `band` — id лидера группы боя), `label: str` (как держателя видит мастер: «вожак гоблинов Клыка», ≤80),
`location_id: str | None` (где искать: логово группы / локация боя), `since_s: int` (время мира), `qty: int = 1`.
- Ведётся только для **кастомных** предметов (SRD-ценности из грабежа уходят безвозвратно, как сейчас — В12).
  Отслеживаются все кастомные (дёшево), в контекст мастера идут только `quest`.
- Перенос держателя — одна функция `rules/custom_items.py::hand_over(world, item_id, holder)` и
  `recover(world, item_id)` (holder=None). Остальной код держателя не трогает.

**Откуда берётся держатель (`combat/defeat.py`):**
- `do_rob`: `pick_valuables` больше не исключает квестовые (обычные правила выбора по цене). Для каждого взятого
  кастомного — `hand_over` с держателем по `state.defeat_group_id`: лидер группы — именованный NPC
  (`leader_id in world.npcs`) → `kind="npc", ref=leader_id`; иначе `kind="band", ref=leader_id`,
  `label` = имя участника-лидера (`Participant.name`/имя монстра) + «банда», `location_id = lair_of(...)` или
  локация героя. Нет группы поражения → `kind="location"`, ref = локация героя («обронил/потерял»).
- `do_capture`: квестовые не остаются у героя, а `hand_over(kind="location", ref=lair, label="тайник логова")`;
  прочие предметы — как было (очищаются). Это даёт сюжетную цель побега.
- Атомарность: держатель пишется в `work.world` того же хода, что и снятие из инвентаря (как сейчас rob/capture).

**Возврат предмета (ни одного нового инструмента):**
- `give_item custom_N` (overlay уже позволяет) для предмета с holder → accepted, `recover` (holder=None), лог
  «Возвращён предмет: <name>». Это путь для переговоров/выкупа/обыска тайника — решает мастер (как В4).
- Автоматика после боя: при `victory` если среди поверженных (dead/down/surrendered, не fled) есть участник с
  `ref == holder.ref` (npc/band) — предмет кладётся в трофеи боя `LastCombat.gear` (раздел 7) и выдаётся вместе с ними.
  Держатель `band` с безымянным лидером: ref лидера боя-грабежа не совпадёт с участником будущего боя (рефы
  пересоздаются) → для `band` автоматики нет, только `give_item` мастером по следу (В11).
- `give_custom_item` с тем же именем (дедуп) для предмета с holder → тот же id + `recover` (защита от дубля, если
  мастер забыл id).
- `take_item` квестового героем вручную (why=given/sold, отдал NPC) — держатель **не** ставится автоматически;
  опциональный параметр `TakeItem.holder_npc_id` — В13 (рек.: не в этой вставке).

**Правило рассказчика (`narrator_rules.md`, рядом с правилом сюжетных предметов):**
«В контексте `lost_items` — сюжетные вещи героя, оказавшиеся у других: у кого (`holder.label`), где искать
(`holder.location_id`), с какого времени. Они не исчезли. Наводи героя на след через мир (слухи, следы, торговец,
пленник), не выдавай вещь просто так. Вернуть — только сюжетно: победа над держателем, сделка, кража, обыск
тайника; тогда `give_item <id>` (id из `lost_items`). Не создавай дубль через `give_custom_item`.»

**Пересечение с BACKLOG 20 «живые NPC» (не реализуем):** `kind="band"` — временная форма безымянного держателя.
Когда п. 20 будет материализовать выживших в `world.npcs`, он же переводит держатель `band(ref=лидер)` →
`npc(ref=новый npc id)` (одна функция миграции данных в п. 20, контракт: `hand_over`). `faction` в модели заложен
для п. 20 / мастера, в этой вставке движок его не ставит. Модель держателя не дублирует NPC-данные (только ref+label).

## 7. Предметы с тел врагов (партия В, BACKLOG 22 п. 1)
Сейчас: `combat/end.py::settle_ground` отдаёт победителю выбитое/брошенное (сдавшиеся — `disarm.py::surrender_drop`);
`LastCombat.defeated` — monster_id (включая fled); `gold_loot` (`protocol/handlers/resources.py`) выдаёт деньги
`loot.defeated_treasure` один раз (`looted`). Оружие поверженных пропадает.

**Модель:** `LastCombat.gear: list[InventoryEntry] = []` (item_id SRD/custom + qty — тот же формат, что инвентарь;
записи несут `cost_cp`/`quality` — торговля п. 23 продаёт по `entry.cost_cp`, раздел 8), `gear_looted: bool = False`.
**Расчёт — в момент конца боя** (`game/combat_flow.py`, где строится `LastCombat`), функция
`rules/loot.py::body_gear(bodies, registry, cfg, hero) -> list[InventoryEntry]` (чистая, тестируемая):
- тела = враги со статусом `dead`/`down` (не `fled` — убежал с оружием; не `surrendered` — его оружие уже на земле и
  отдано через `settle_ground`; не перебежчики);
- оружие тела = `disarm.weapon_ids(engine, ref)` **после** боя — выбитое/брошенное уже не числится, двойной выдачи нет;
  фолбэк по контенту: уникальные `MonsterAction.weapon_id` монстра. Природные атаки (без weapon_id) ничего не дают.
  Доспехи монстров в модели не описаны → не выпадают (В14).
- каждое оружие → вариант по ПО тела (таблица ниже); плюс квестовые кастомные, чей держатель среди тел (раздел 5).
- Только при `victory`/`ended_by_master` и живом герое (как `settle_ground`).

**Правило баланса — цена, а не лимит количества** (решение проектировщика, ред. 2). Рядовое оружие выпадает всё,
но стоит дёшево; дорогое — только с сильных врагов и боссов.
Таблица качества по ПО тела (`[loot].trophy_quality` в `config/defaults.toml`, полосы как `loot.treasure_band`):

| ПО тела | качество (`quality`) | префикс названия | множитель к цене SRD |
|---|---|---|---|
| 0 – 1/4 | `junk` | «ржавый» | ×0.1 |
| 1/2 – 2 | `worn` | «поношенный» | ×0.25 |
| 3 – 4 | `used` | «потёртый» | ×0.5 |
| 5+ или босс | — (исходный SRD-id) | — | ×1.0 |

- Босс = лидер группы (`Group.leader_id`) **и** именованный NPC (`world.npcs[ref].named` или `key`), либо тег монстра
  `boss`. Босс всегда даёт исходное SRD-оружие независимо от ПО.
- Цена = `max(1, floor(SRD cost_cp × mult))` мм. Вычисляется функцией `rules/loot.py::trophy_cost(base, quality, cfg)`.
- **Хранение (ред. 3, по разделу 8):** трофей — обычная запись инвентаря с собственной ценой:
  `InventoryEntry(item_id="scimitar", qty, cost_cp=<по формуле>, quality="worn")`. Id остаётся SRD — трофей
  полноценное оружие без копий моделей и без каталога вариантов; префикс названия («поношенный») — из `quality` при
  показе. Торговля п. 23 берёт `entry.cost_cp`. (Вариант ред. 2 «`scimitar~worn` в каталоге мира» снят.)
- Боеприпасы, доспехи, магия босса — вне объёма (В14).
- Лимиты количества убраны; остаётся только «оружие из боя не дублируется с выбитым» (корректность, не баланс).

**Выдача — явно, а не автоматически** (как деньги): расширить `gold_loot`-путь: тот же запрос «добыча с тел»
(`loot_individual`, gain) выдаёт деньги **и** `gear`; общий флаг не годится — отдельный `gear_looted`, чтобы старые
сейвы (looted=true) не выдали трофеи. Результат `{amount_cp, money_cp, items:[{item_id, qty, name}]}`, лог
«Добыча: скимитар, короткий лук». Мастер вызывает при обыске тел (правило в `narrator_rules.md` рядом с добычей:
«Обыск тел — один `loot_individual`: даёт деньги и снаряжение, не выдумывай оружие через give_item»). Причина: герой
может не обыскивать (бежать дальше) — ровно как деньги сейчас.
- Контекст мастера: `last_combat` в `master/prompt.py` дополнить `gear: [name]` и `gear_looted`, чтобы мастер
  описывал, что лежит на телах.
- «Получено» и /inv — через `add_item`, правок не требует (кроме теста).

## 8. Цена у каждого экземпляра предмета (уточнение проектировщика, ред. 3)
Требование: любой предмет в мире (инвентарь героя, у держателя, в луте) несёт свою цену: по умолчанию — цена SRD,
трофей — по ПО врага, кастомный — заданная мастером.

**Как сейчас:** `state/hero.py::InventoryEntry(item_id, qty)` — только ссылка на id, цена берётся из реестра
(`find_item(...).cost_cp`) только в `pick_valuables`. `Equipped` — слоты с id. Лут — деньги (`LastCombat`),
`GroundItem(item_id, zone_id, owner_ref, qty)`. Кампании задают инвентарь списком id (`campaigns/*/heroes/*.yaml`,
`rules/builder.py`, `campaign/build.py`).

**Модель (рек. — «стек с ценой», не уникальные экземпляры):**
`InventoryEntry(item_id, qty, cost_cp: int, quality: Literal["junk","worn","used"] | None = None)`.
Стек = одинаковые `(item_id, cost_cp, quality)`; два скимитара разной цены — две строки. Уникальный id экземпляра
(uuid на каждую вещь) не нужен: предметы взаимозаменяемы внутри стека, сейв не раздувается (альтернатива — В19).
- `GroundItem` + `cost_cp`, `quality` (выбитое оружие сохраняет цену владельца; монстру — цена трофея по его ПО).
- `LastCombat.gear: list[InventoryEntry]`, `CustomItem.holder.qty` → держатель хранит и `cost_cp`
  (вернуть с той же ценой).
- `Equipped` остаётся по id (слот = «одна вещь этого id»); правило: надетая вещь — из **самого дорогого** стека
  этого id (снятие/кража не трогают надетую дорогую в первую очередь).

**API `rules/inventory.py` (единственная точка мутаций):**
- `add_item(hero, item_id, qty=1, *, cost_cp, quality=None)` — `cost_cp` обязателен keyword (не забыть в 44 местах);
  хелпер `add_catalog_item(hero, registry, item_id, qty)` — цена из реестра (SRD/кастомный) для обычных выдач.
- `remove_item(hero, item_id, qty=1, *, cost_cp=None)` — None: снимать с **самого дешёвого** стека (расход, отдал),
  конкретная цена — точечно (кража, продажа). Возвращает снятые `InventoryEntry` (для держателя/лута).
- `count_item` — сумма по стекам (сигнатура не меняется: триггеры, бой, `take_item` работают как есть).
- `pick_valuables` — сортировка по `entry.cost_cp` вместо реестра; возвращает записи с ценой.
- `entry_cost(entry)` — просто поле; `entry_name(entry, registry)` — имя + качество суффиксом в скобках («Скимитар (поношенное)»; слова: хлам / поношенное / б/у;
префикс-прилагательное не взяли — не согласуется по роду). Golden `/inv` обновить в партии Б.

**Наложение на реестр (пересмотр):** нужно **только для кастомных** — имя/описание/категория/«квест» для
`find_item` в ~35 местах. Для цены и трофеев оно больше не нужно (цена в записи, трофей — SRD-id). Рек.: overlay
оставить (раздел 1), но `CustomItem.cost_cp` становится ценой по умолчанию при выдаче, а не источником для продажи.
Альтернатива «экземпляр несёт name/description сам, без каталога» отклонена: ломает держателя/дедуп и
`find_item` (В20).

**Миграция v6 (дополнение к разделу 6):** каждой записи `hero.inventory`, `npc.creature`-инвентарей (если есть) и
`combat.ground_items` проставить `cost_cp` = цена SRD по id. Миграции сейчас чистые `dict → dict` без реестра →
рек.: расширить `migrate(data, *, context=None)` объектом `MigrationContext(item_cost: dict[str, int])`, который
`persistence/store.py` строит из реестра при загрузке (реестр уже есть в `ui/cli.py::load_registry` до загрузки
сейва — проверить порядок). m0006 не импортирует модели state/content — получает только dict цен. Неизвестный id →
`cost_cp=0` + запись в отчёт миграции (не падать). Бэкап слота — как в разделе 6 (`make_backup` автоматически).
`quality` старым записям не ставится (None = «как новый»). Фикстуры v0..v5 проходят цепочку с context.

**Объём правок (оценка по grep):**
- `rules/inventory.py` — ядро (add/remove/count/pick_valuables/equip/use/drink): средне.
- Вызовы `add_item/remove_item/count_item/find_item` — 44 места в 19 файлах; реально меняются только `add_item`
  (~12: `protocol/handlers/resources.py`, `combat/end.py::settle_ground`, `combat/disarm.py`, `campaign/build.py`,
  `rules/builder.py`, `combat/actions/attack.py`) и `remove_item` с возвратом (defeat, disarm). `find_item` — без изменений.
- Прямые обходы `hero.inventory` (8 мест): `/inv` `game/sheet_text.py:150` (стек с качеством — отдельная строка
  «поношенный скимитар ×2», цена стека), «Получено» `ui/screen.py:182,192` (сейчас словарь `item_id → qty` — **ломается
  при двух стеках одного id**, перевести на ключ `(item_id, cost_cp, quality)`), бой `combat/available.py:67,226`,
  `combat/actions/attack.py:65` (по id — достаточно агрегата), `master/prompt.py:276` (+ cost_cp, quality),
  `rules/triggers_eval.py:107` (any по id — ок), `combat/defeat.py:82`.
- Тесты: ~40 файлов упоминают inventory, 9 конструируют `InventoryEntry` напрямую → `cost_cp` обязателен ⇒ правка
  этих 9; остальные через `add_item` ⇒ правка вызовов. Golden-контекст мастера — перегенерировать.
- Итого: отдельная партия «0» среднего объёма (~1–1.5 партии А), делать **первой** — на ней стоят А–В.

## Риски
- Реестр-свойство пересоздаётся: кэш обязателен, иначе `with_items` копирует весь реестр на каждый вызов (дорого
  в TUI-перерисовке). Ключ кэша — по содержимому каталога, не по `id(world)` (ход работает на копии bundle).
- `CombatEngine` получает реестр при старте боя: кастомный, выданный в бою (через improvise/рассказчика), не будет
  в реестре движка до конца боя → проверить, что движок берёт реестр из runner на каждый ход, либо выдача только вне
  боя (рек.: в бою разрешить, движку предмет не нужен — он не оружие/расходник; проверить available.py на None).
- LLM будет злоупотреблять (каждую ложку — предметом): per_scene + правило «только сюжетно значимое».
- Цена кастомного не конвертируется в деньги (продажи в движке нет) — кап нужен на будущее (п. 22 / торговля).
- extra=forbid в WorldState: без миграции/default старые сейвы упадут — покрыто тестом фикстуры v5.
- Держатель-band после боя теряет связь с живыми участниками (рефы одноразовые): вернуть можно только волей мастера —
  риск «забытого» предмета. Смягчение: `lost_items` всегда в контексте (с потолком 5 записей, самые свежие), п. 20
  переведёт band → npc.
- Если держатель-NPC умер вне боя (world_sim mortality) — предмет «на теле»: рек. при смерти NPC держатель меняется
  на `location` = его последняя локация (правка в world_sim — В15, может уйти в п. 20).
- pick_valuables теперь берёт квестовые: грабёж может забрать сюжетный ключ в самый неудобный момент — так задумано
  (В3), но нужен лог для игрока «Отобрано: Ржавый ключ — у <label>» (иначе выглядит как баг).
- Трофеи: `weapon_ids(engine, ref)` требует движок; если в `combat_flow` движка уже нет — считать в `combat/end.py`
  (conclude) и класть в CombatState → проверить на месте, порядок `settle_ground` → `body_gear` обязателен.
- Одна версия v6 на три партии: нельзя выпускать А без В (иначе v7). Если В задержится — рек. всё равно добавить поля
  `gear/gear_looted` в партии А.
- Много ржавого хлама в инвентаре (нагрузки нет) — шум в /inv; смягчение: стек одной строкой, при торговле продаётся.
- Экономику покажет п. 23; коэффициент продажи (напр. ½ цены) — решение п. 23, поверх цены варианта.

- Партия 0 трогает всё ядро инвентаря: риск регрессий в бою (расходники, боеприпасы, обезоруживание) — полный
  прогон + `make mutate TESTS=` по `rules/inventory.py`.
- «Получено» сейчас агрегирует по id → после партии 0 обязателен ключ стека, иначе прирост трофея при наличии
  такого же SRD-предмета посчитается неверно.
- Миграция с реестром: сейв, открытый с другим набором контента (моды/кампания), получит иные цены; цены фиксируются
  один раз при миграции — это ожидаемо, но задокументировать.
- `Equipped` по id при нескольких стеках — неоднозначность «какая именно вещь надета»; правило «самый дорогой»
  простое, но продажа надетого (п. 23) должна его учитывать.

### Замечания (по важности)

#### Важные
1. **`peek_campaign_id` читает manifest раньше, чем `recover_slots`** — `persistence/store.py::peek_campaign_id`,
   `ui/cli.py::prepare`. Если запись слота прервалась (manifest лежит в `.tmp-*`/`old`), `load_slot` бы его
   восстановил, а peek падает с FileNotFoundError, и игрок видит «Нет автосохранения». Предлагаю вызывать
   `recover_slots(root, world_id)` в начале `peek_campaign_id` (или прямо перед peek в `prepare`).
2. **Реестр в cli берётся по campaign_id из manifest до миграции, а после загрузки не сверяется** — `ui/cli.py::prepare`.
   m0003 проставляет `campaign_id="vale"` при миграции, поэтому у v0–v2 сейвов peek возвращает None. Сейчас это не
   ломается, потому что у vale нет `content/`, но `registry` и `pack_dir` остаются от None, а `campaign_id` уже
   берётся из `bundle.world.campaign_id`. Предлагаю после загрузки так: если `bundle.world.campaign_id != campaign_id`
   из peek, пересобрать `pack_dir, registry = campaign_registry(...)`. Это одна проверка, зато пак и реестр
   гарантированно совпадут.
3. **Отчёт миграции нигде не показывается** — `store.py::load_slot` / `game/app.py::load` / `cli.py`. В плане сказано
   «неизвестный id → cost_cp=0 + запись в отчёт миграции», но `context.report` после загрузки никто не читает (а
   контекст, который строится внутри `load_slot`, вообще недоступен снаружи). Предлагаю хотя бы
   `say(notes, ...)` в cli и строки в ответе `GameApp.load`, если `context.report` не пустой. Без этого предметы с
   ценой 0 появятся молча.
4. **Запасной вариант `load_slot` без контекста (встроенный реестр)** — `store.py::load_slot`. Оба реальных вызова
   (`cli.prepare`, `GameApp.load`) передают пакетный реестр, поэтому в игре цены паковых предметов правильные.
   Риск в будущих вызовах (инструменты, тесты, партия А): у предметов `drunk_dragon/content` молча станет
   `cost_cp=0`, ведь отчёт теряется (п. 3). Кроме того, `persistence` теперь импортирует `content.loader`, что
   нарушает слой, который сам план и защищал («m0006 получает только dict цен»). Предлагаю убрать запасной вариант
   и сделать `context` обязательным при `version < current_version` (уже есть `MigrationContextRequired`), а тестам
   передавать `MigrationContext.from_registry(load_registry())` явно. Если оставлять, то хотя бы добавить строку в
   `context.report`: «цены из встроенного реестра».
5. **`remove_item(cost_cp=...)` не учитывает quality** — `rules/inventory.py::remove_item`, `combat/defeat.py::do_rob`.
   Стек определяется тройкой `(item_id, cost_cp, quality)`, а точечное снятие идёт только по паре `(id, cost)`. В
   партии 0 качества ещё нет, но в партии В появятся трофеи с качеством. При совпадении цены у двух стеков, например
   «поношенный» по ПО и SRD с той же ценой, `pick_valuables` вернёт одну запись, а снимется другая (сначала
   дешёвая сортировка, при равной цене первая по порядку). Предлагаю добавить `quality=...` в `remove_item` (по
   аналогии с cost_cp: None — любой) и передавать его из `do_rob`. Сейчас это дешевле, чем потом в партии В.

#### Средние
6. **`pick_valuables` всё ещё кидает InventoryError на неизвестный id** — `rules/inventory.py::pick_valuables`. Цена
   теперь берётся из записи, реестр в функции нужен только ради этой проверки. В тестах плана (партия А) записано:
   «неизвестный id пропускается без исключения». Как отклонение партии 0 это допустимо, раз поведение не менялось.
   Но в партии А кастомный id без overlay сломает грабёж (`do_rob` упадёт). Пометить в HANDOFF/плане как
   обязательный пункт партии А, а лучше просто удалить проверку уже сейчас: она больше ничего не защищает.
7. **Звезда «надето» в `/inv` при равной цене** — `game/sheet_text.py::inv_lines`. `is_worn` = `cost_cp ==
   dearest_cost`: если у двух стеков одна цена и разное качество, звёздочки получат оба. Пока качества нет, это не
   проявится. Для партии В достаточно отмечать только первый стек с максимальной ценой (флаг «уже отметили» по id).
8. **Цена выбитого у монстра = SRD** — `combat/disarm.py::strip_weapon`. По плану здесь нужна «цена трофея по ПО»,
   kaban сознательно отложил это на партию В. Приемлемо: GroundItem уже несёт цену, в партии В поменяется одна
   строка. Нужен TODO/пункт в плане партии В: «`strip_weapon` монстра → `trophy_cost`», иначе забудется, и выбитое
   оружие рядового врага останется дороже трофея с его тела (это противоречит решению по балансу).
9. **`WITH_CONTEXT = {5}` завязан на номер версии, а не на конкретную функцию** — `persistence/migrations/__init__.py::migrate`.
   Если в тестах подменить цепочку (`registry=`) и положить на ключ 5 свою функцию с одним аргументом, вызов
   сломается. Проще по-джуновски: передавать context всем миграциям (`fn(data, context)`, старые принимают
   `context=None` и игнорируют) или проверять `fn is migrate_v5_to_v6`. Не блокер.

#### Мелкие и стиль
10. Модель `PackItem` для паков — отклонение разумное: в YAML пака цены нет, она берётся из реестра при сборке через
    `add_catalog_item`. Других вариантов не вижу. Оставить.
11. Качество в скобках, «Скимитар (поношенное)»: в плане префикс («поношенный скимитар»), но с прилагательным
    пришлось бы согласовывать род («поношенный/поношенная/поношенное»). Суффикс в скобках проще и корректен для
    любого рода. Принять, но обновить план (раздел 8, `entry_name`) и golden `/inv` в партии Б. Слово «б/у» для `used` в
    скобках читается нормально.
12. `combat/available.py::item_options` — тернарник `note = ... if ... else ...` заменил явный if/else. Это
    постороннее переформатирование, не нужное для задачи (CLAUDE.md просит не трогать лишнее). Вернуть if/else.
13. `migrate_v5_to_v6` не трогает `world.npcs` и компаньонов. Проверил: инвентарь в state есть только у `HeroState`,
    так что это корректно. `LastCombat.gear` появится в партии А и сразу должна писаться с cost_cp (миграция той
    же v6). Это совместимо, потому что m0006 через `fill` пропускает записи, где `cost_cp` уже есть.
