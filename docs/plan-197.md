## Оценка

### 1. Насколько ядро отделено от TUI

Измерено (`wc -l`, 2026-10-30): `src/ai_dm` — 37 671 строка; `ui` — 4 766 (12,6 %), из них `ui/tui/*` 2 049,
`cli.py + simple.py + io.py + format.py` 1 377, слой сессий и блоков (`session.py`, `hero_session.py`, `hero_wizard.py`,
`import_session.py`, `key_session.py`, `screen.py`, `combat_menu.py`) 1 340. `game` — 5 073.

Что уже хорошо (проверено grep и тестами-сторожами):
- Ничто вне `ui` не импортирует `ai_dm.ui` (grep пуст; сторож `test_nothing_but_ui_imports_ui`); `game` не импортирует
  `ui` и SDK (`test_game_does_not_import_ui_or_sdks`). Направление `ui → game → master → llm` (ARCHITECTURE C1) держится.
- `GameApp.handle(line) -> Reply` и `GameApp.choose(key) -> Reply` — синхронный фасад без ввода-вывода (C1); меню —
  `pending` + `menu_for`. Это уже «контроллер» для любого клиента.
- `PlaySession.submit(line) -> Step{blocks, quit, request, events}` и `Block{kind, text, items, title, args}` — готовый
  транспортный формат: виды `narration, roll, note, boundary, raw, hint, menu, combat_map, turn_menu, combat_hint,
  status, gains` сериализуются в JSON без правок. Простой режим и TUI уже два клиента одного `Step` (simple.py:93,
  tui/app.py:449) — третий (веб) встаёт туда же. То же у создания героя (`HeroSession`/`HeroWizard`), ключа
  (`KeySession`) и импорта пака (`ImportSession`).
- Часы, ожидание, ключи, пути инъецируются: `GameApp(now=, sleeper=, saves_root=, campaigns_dir=, adapter_factory=)`,
  `make_adapter(env=, dotenv_path=)`. Серверу не нужен `~/.config/ai-dm`, `.env` и `os.environ` игрока.
- Данные мира — каталог `saves/<world_id>/` целиком (слоты, `meta/`, `journal/`, `issues/`): «один игрок = один
  `saves_root`» даёт изоляцию без правок persistence.
- Замеры (python-скрипт в сессии, живой мир `drunk_dragon-00000001`, только чтение): `load_registry([])` 0,38 с;
  `load_slot` 0,08 с; `model_copy(deep=True)` 12 мс; бандл 440 205 байт JSON (58 NPC, 50 ходов); `save_auto` ≈ 60 мс
  при `durable=True`, ≈ 9 мс без fsync; слот `auto` на диске 784 КБ; `journal/` живого мира (≈ 1 340 ходов) 57 МБ.

Что мешает другому клиенту (по убыванию веса):
1. **Корень сборки — в `ui/cli.py:prepare` (:896–1111, 215 строк)**: создание/загрузка мира, реестр пака
   (`campaign_registry`), адаптеры трёх ролей, ветка создания героя, replay — всё читает `args`, `stdin`, `notes`.
   Сервер не может вызвать `prepare`, а копировать — двойная логика. Нужен `game/bootstrap.py` (новая) с чистыми
   функциями «открыть мир» / «новый мир» → `GameApp`; cli остаётся тонким вызывающим. Регресс-риск: 48 тестов `tests/unit/ui`
   (`test_cli_*`, `test_ui_cli*`) — часть мокает `prepare` по сигнатуре.
2. **Ход блокирует поток на 10–60 с** (`TurnRunner.play` → `MasterSession.call` → `call_with_retries(sleeper=time.sleep)`;
   медиана ≤ 45 с по 207). Стрима нет (207, решение 2). TUI прячет это в `run_worker(thread=True, exclusive=True)`.
   Серверу — пул потоков и замок на мир; ядро не трогается.
3. **Автосейв только на границе сцены** (`boundary.py:253`) и при выходе (`PlaySession.finish`, `cmd_quit`). Падение
   процесса сервера теряет ходы с последней границы (до 30 ходов, D3). Сейв 60 мс — автосейв каждый ход дёшев, но это
   правка `GameApp.after_turn` или обёртки сервера.
4. **Команды и запросы, рассчитанные на локальную машину:** `/key` (`cmd_key` → `Reply.request="key"` → окно ввода
   ключа), `/music` (TUI), `/quit` («сохранить и выйти» процесса), `/model` (смена модели — на сервере решает тариф),
   `/report` пишет в `saves/<world>/issues` (на сервере — полезно, но читать будет автор). Серверу — фильтр `COMMANDS`
   (конфиг или параметр `GameApp`), не правка команд.
5. **`CostLedger.report` считает «день» по всем мирам `saves_root`** (`glob("*/meta/costs.jsonl")`). При общем корне
   для всех игроков строка состояния покажет чужие траты; при корне на игрока — верно. Лимиты 199 всё равно лучше
   считать сервером (таблица), а не этим отчётом.
6. **Один конфиг на процесс** (`load_user_settings`, `[llm]`, `[master]`, профили) — для сервера это норма (настройки
   оператора), но `ui.width`, `[audio]` — личные; слой блоков берёт `width` из `app.settings.app.ui.width`
   (`combat_map_lines`) и из `HeroSession.width` — веб-клиенту ширину задавать нечем, карта боя придёт на 80 колонок.
7. **Глобалы процесса:** `persistence/durable.DURABLE` (ставится один раз — ок), `protocol/schema._cache`,
   `content/handlers.HANDLERS` (статика), транспорт Gemini `local_address` (gemini_adapter.py:67) — один на процесс, ок.
   Реестр контента на мир (`campaign_registry` по паку) — повторная загрузка 0,38 с, кэш по `campaign_id` решает.
8. **`screen.py` импортирует `art` и `audio`** (`PictureState`, `SoundState`) — это данные, не Textual; веб-клиенту
   `picture_state` даже полезен (картинка локации/монстра). Не мешает.
9. **Журнал 57 МБ на 1 340 ходов** — на сервере ×игроков; есть ротация `JournalConfig.max_mb` — хватит настройки.
10. **Тесты клиента:** 21 файл Pilot-тестов `tests/unit/ui/tui` (маркер `slow`, флаки BACKLOG 216/226) — веб-клиенту
    нужны свои тесты, но без Textual: HTTP-клиент + mock-адаптер (`--mock` путь уже есть: `mock_factory`, `ScriptedAdapter`).

Вывод: ядро отделено хорошо — граница `GameApp`/`Step`/`Block` уже существует и проверена двумя клиентами. Долг один:
корень сборки в cli (п. 1). Остальное — обвязка сервера, не ядро.

### 2. Что нужно для веб-клиента (минимум 198)

1. `game/bootstrap.py` (новая): `open_world(saves_root, world_id, settings, adapters) -> GameApp`,
   `new_world(saves_root, campaign_id, hero, preset, difficulty, seed, ...) -> GameApp`, `registry_for(campaign_id)`
   с кэшем; из `prepare` переезжают строки :942–1075 и :1091–1111; `prepare` зовёт их. Поведение cli не меняется.
2. Серверное приложение (пакет `src/ai_dm/web/`, при Р3 = «в репо»): HTTP-API поверх `PlaySession`/`HeroSession`:
   список миров игрока, новый мир (пак, герой, пресет, сложность), `turn {line}` → `Step` в JSON, `choose {n}`,
   справочные команды как есть (`/sheet`, `/inv`, `/lore` — блоки `note`/`raw`). Один запрос хода живёт до ответа
   модели (до ~120 с) — при Р4 = «HTTP + спиннер».
3. Клиентская страница: лента блоков, поле ввода, нумерованные варианты и меню боя (`turn_menu`), карта боя (`raw`),
   строка состояния; мобильная вёрстка (у banshee — браузер, значит сравнивают с ним). При Р5 = «SSR + htmx» — Jinja-шаблоны в
   `web/templates`, JS ≤ 200 строк (ожидание, не проверено).
4. Аккаунты и сессии (198г): пользователь, cookie-сессия, `saves_root = <data>/<user_id>/` (изоляция файлов,
   `CostLedger` на игрока, `/report` на игрока). Хранилище учёток — при Р6 = SQLite (`sqlite3` stdlib, без новой
   зависимости); таблицы `users`, `sessions`, `worlds(user, world_id, created, last_turn)`, `turns(user, ts, cost_nano,
   model)` — последняя кормит 199.
5. Ключи: только серверные (`env` оператора через `make_adapter(env=)`), модель рассказчика — из серверного
   `config.toml` (`narrator_chain`, профиль V4-Flash по NOTES 2026-10-27); `/key`, `/music`, `/quit`, `/model` — вне
   набора команд сервера (фильтр `COMMANDS`); `Reply.request="key"` сервер игнорирует.
6. Конкурентность: один процесс `asyncio` (FastAPI/uvicorn 0.162.0, живой — или aiohttp, уже в зависимостях
   textual-serve, но не наших), пул потоков под ходы (`asyncio.to_thread`), `threading.Lock` на мир, кэш загруженных
   `GameApp` с выгрузкой по простою (сейв при выгрузке), автосейв после каждого хода (п. 3 выше). Память: бандл
   440 КБ JSON → объекты Pydantic ≈ единицы МБ на мир (ожидание, не измерено); сотня одновременных миров — один
   процесс на 4–8 ГБ (ожидание, не проверено). Модель-хостер держит параллельность за нас (research §3).
7. Развёртывание: VPS в РФ (152-ФЗ) 2–4 vCPU / 4–8 ГБ, systemd, Caddy (TLS), бэкап `data/` по расписанию; инструкция
   `docs/howto-server.md` (новая, по COMMON «howto-<тема>»).

Что НЕ нужно для минимума: переписывать `game`/`master`/`protocol`; стрим; WebSocket; Postgres; отдельный фронтенд-репо;
менять формат сейва (у сервера те же `saves/<world>/`, миграции общие с открытой версией).

### 3. Несколько игроков на одном сервере

При Р0 = «много одиночных миров» (не кооператив):
- Состояние сессии: `GameApp` в памяти на активный мир, ключ `(user_id, world_id)`; ход — под замком мира; второй
  запрос во время хода — `409`/«ход идёт» (как `busy` в TUI). Простой > N мин → `save_current("auto")` и выгрузка;
  повторный вход — `load_slot` 0,08 с + реестр из кэша.
- Сейвы: `saves_root` на игрока; слоты, `meta/`, `journal/`, `issues/` — как в открытой версии; квоты на диск —
  `JournalConfig.max_mb` + `reports.max_mb` (есть). 100 игроков × (слоты ≈ 1–3 МБ + журнал до `max_mb`) — десятки ГБ
  при текущем журнале (ожидание; живой мир — 57 МБ журнала на 1 340 ходов, измерено).
- Ключи API: у сервера, в `env` процесса; игрокам не выдаются. BYOK на вебе (игрок приносит ключ) — Р7, по умолчанию нет.
- Конкурентность: сетевые вызовы синхронные в потоках; ядро детерминировано и не делит состояние между мирами
  (глобалы — статика). Одного процесса хватает до сотен активных игроков (ожидание по research §2: 31 ход/ч на игрока,
  ход ≈ 45 с ожидания сети, CPU-работа хода — миллисекунды: deepcopy 12 мс, сейв 60 мс).
- Лимиты (199) — на сервере по таблице `turns`: окна 5 ч и неделя, остаток в ходах; `check_limit`/`CostLedger` остаются
  для «/cost» игрока, а не для тарифов.
- Кооператив (общий мир нескольких игроков) — отдельный продукт: протокол рассказчика рассчитан на одного героя
  (`hero_of(bundle)`, `current_hero_id`), меню боя — на одного; в оценку не входит.
