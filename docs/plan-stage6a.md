## A. Архитектура

- Новый пакет `src/ai_dm/reports/` (заявлен в ARCHITECTURE): `__init__.py`, `capture.py` (что снять с хода), `writer.py`
  (каталог репорта, report.md, копия журнала и блобов), `markdown.py` (текст отчёта, чистые функции), `replay.py` (загрузка
  репорта, прогон, сравнение).
- Слой: `reports` импортирует `state`, `persistence`, `llm.journal`, `llm.replay`, `core`; **не** импортирует `game`, `ui`,
  `master`. Его вызывает `game` (запись) и `ui.cli` (`--replay-report`). Прогон хода в `reports/replay.py` нельзя делать
  через `TurnRunner` (это `game`) — поэтому `reports/replay.py` только **готовит** вход (бандл до хода, адаптеры по ролям,
  фраза, `now`, ожидаемый результат) и **сравнивает**; сам ход крутит `ui.cli` через обычный `GameApp`/`TurnRunner`.
  Сторож в `tests/unit/test_architecture.py`: `REPORTS_FORBIDDEN = ["game", "ui", "master"]` + `reports` уже в списке
  запрещённых для нижних слоёв (стр. 9, 259) — оставить.
- Формат репорта на диске — каталог (ТЗ 9 «markdown-файл» + вложения по В2; аудит это отметил — считаем принятым В2):
  ```
  saves/<world>/issues/<YYYYMMDDTHHMMSS>-t<turn_seq>-<метка|manual>/
    report.md                 # человекочитаемый отчёт
    meta.json                 # машинное: версия формата репорта, run_ids, фраза, now, теги, статус, модели по ролям
    before/                   # слот снимка ДО хода (write_slot, текущая версия схемы)
    after/                    # слот снимка ПОСЛЕ хода (только принятый ход)
    journal/calls.jsonl       # записи журнала всех run_id хода, в порядке записи
    journal/blobs/<sha>.json  # блобы system/tools этих записей
  ```
  `meta.json` получает собственное поле `report_format: 1` (не версия сейва).
- Ключи (C4, Т3): репорт собирается только из бандла и журнала, ключей там нет. Тест-сторож обязателен.

### P1. Полный репорт: N ходов, снимки, вызовы хода копией

1. Конфиг: `config/app.py` — `ReportsConfig(recent_turns: int = 5)` в `AppConfig` (+ дефолт в файле конфига, если он
   перечисляет блоки). Не версия сейва.
2. `reports/writer.py`:
   - `before/` — `write_slot(...)` снимка до хода; `after/` — снимок после (только `committed`).
   - `journal/calls.jsonl` — записи журнала с `run_id ∈ capture.run_ids` (`Journal.read_records()` с фильтром; читать с
     конца, как `mark_turn`, чтобы не разжимать весь журнал — новая функция `Journal.records_for(run_ids)` в `llm/journal.py`);
     блобы `system_sha256`/`tools_sha256` — копией. Записи пишутся после `mark_turn`, т.е. с итоговым `turn_status`.
   - в `report.md`: последние N ходов из `before.memory.recent_turns` (+ сам ход из `after`, если принят) — фраза, рассказ,
     броски; если `recent_turns_keep` < N — сколько есть, с пометкой; «сырой запрос/ответ» — по каждому вызову хода: роль,
     модель, attempt, stop_reason, сообщения запроса и ответ (системный промпт и tools — ссылкой на блоб в каталоге, не
     инлайном: объём).
   - модель: из записей журнала по ролям (`model`, `requested_model`); при смене `/model` в сессии — то, что реально ушло
     в вызовах хода (закрывает замечание аудита «какая модель»).
3. Ход без вызовов модели (боевое действие по номеру) — `calls.jsonl` пустой, это норма.
4. Ручной `/report` — относится к последнему ходу (`last_capture`), N ходов и снимки те же; после `/load` `last_capture`
   сбрасывается (иначе снимок от другого мира/слота).
5. Журнал выключен (`journal is None`) — репорт без `journal/`, в `report.md` строка «журнал отключён, воспроизведение
   невозможно»; `meta.json.replayable=false`.

Тесты P1:
- `before/` и `after/` грузятся `load_slot` и равны бандлам до/после (сериализованное сравнение, Т4).
- Откатанный ход: `before` есть, `after` нет; `before` равен состоянию игры после отката.
- `calls.jsonl` содержит ровно вызовы хода: повторы после transient (attempt 2), вызовы `world`/`summarizer` границы, не
  содержит вызовов соседних ходов; все упомянутые блобы скопированы.
- Ротация: после репорта журнал мира ротируется/удаляется (`max_mb` маленький) — каталог репорта не меняется, остаётся
  полным (смысл копии по В2).
- N: `recent_turns=5`, сыграно 7 ходов → 5 в отчёте; сыграно 2 → 2.
- `/load`, затем `/report` → снимок текущего, без раздела хода.
- Журнал выключен → `replayable=false`, файл есть.
- Сторож ключей повторить на полном репорте (теперь там запросы целиком).

### P2. `ai-dm --replay-report <каталог>` и критерий ТЗ 13

1. `reports/replay.py`:
   - `load_report(path) -> ReportReplay`: `meta`, бандл `before` (`load_slot` во временный `saves_root`: каталог копируется
     во временную папку, живой `saves/` не трогается), записи по ролям, фраза, `now_iso`, ожидание (`after` или
     «откат + причина»).
   - Из ревью P1: блоб записи журнала не найден при записи репорта → `replayable=false` (сейчас молча пропускается);
     `saved_at` снимков — время записи репорта, исключить из сравнения.
   - `compare(expected, actual) -> list[str]` — расхождения по сериализованному бандлу, с исключением полей времени
     реального мира (`saved_at` и подобных — список держать в одном месте, проверить разработчику по дампу).
2. Детерминизм (риск грумера, проверять **первым**):
   - `TurnRunner.stamp` и `run_id` строятся из `now()` → в replay передавать `now` = зафиксированное `meta.now_iso`
     (параметр `now` у `TurnRunner`/`GameApp` уже есть). Проверить, не попадают ли `run_id`/время в сообщения запроса
     (иначе `ReplayDivergence` по отпечатку).
   - `run_count`/`boundary_count` — у нового раннера с 1; в meta писать номер, replay выставляет его (или отпечаток не
     зависит от run_id — тогда не нужно).
   - Модели запроса — из записей журнала (как `journal_role_model` в cli).
3. `ui/cli.py`: флаг `--replay-report PATH`; несовместим с `--new/--world/--replay/--mock*` (сообщение и код 2). Поток:
   `load_report` → `GameApp(..., auto_reports=False, use_stored_model=False, now=fixed)` с `ReplayAdapter` по ролям
   (narrator/world/summarizer; роль без записей — как в нынешнем `--replay`) → `app.handle(player_input)` (или `retry`-путь,
   если ход был достройкой границы) → `compare`. Вывод: рассказ хода, затем «Состояние совпало» (код 0) или список
   расхождений / `ReplayDivergence` (код 1). Для откатанного: ожидается тот же `failure.reason` и состояние == `before`.
   `replayable=false` → сообщение, код 2.
4. Документы: README (как воспроизвести репорт), ARCHITECTURE (`reports`, поток replay), HANDOFF.

### Вердикт
Не готов до ответов на В1–В6. Этап — пять разных задач под одной строкой. Критерий проверяет только две (репорт и
воспроизведение). Для import, героя на лету и предыстории критерия нет. Сразу можно делать P0: сбор меток хода в репорт-файл
и сам формат файла. От ответов это не зависит, кроме В2 (содержимое) — берём минимум из ТЗ 9.

### Суть
1. Репорты (ТЗ 9): `/report <текст>` и авто-метки `missing-mechanic`, `limit-exceeded`, `invalid-death`, `refusal` →
   markdown в `issues/`: текст, последние N ходов, снимок состояния, сид и состояние RNG, модель, сырой запрос/ответ. Без ключей.
2. Воспроизведение (ТЗ 11): сид + ответы из журнала → точный повтор хода. Репорт несёт нужный фрагмент журнала.
3. `import` (ТЗ 3): текстовая выжимка → ИИ раскладывает по файлам пака → пользователь правит руками.
4. Герой на лету (ТЗ 5, 5.2): описание словами → ИИ предлагает лист → движок валидирует → игрок подтверждает/правит;
   альтернативно пошаговый классический режим; мотив/средства/возможности героя.
5. Свободная предыстория (ТЗ 6): описание словами → ИИ раскладывает по структуре 5.2 → валидатор (3 характеристики,
   2 навыка, инструмент, черта происхождения, снаряжение+золото ≤ 50 зм); 4 SRD — примеры для модели.
Критерий ТЗ 13: «/report и авто-метки создают файл; ход из репорта воспроизводится по сиду + журналу с идентичным состоянием».

### Чего нет
- Модуля `reports` (ARCHITECTURE его заявляет), каталога `issues/`, записи файла репорта.
- Метки `refusal` в `report_tags`: отказ идёт как сбой хода, метки нет.
- Метка `context_overflow` (ARCHITECTURE C4/память) объявлена в архитектуре, но в коде не найдена grep'ом. Гипотеза:
  ставится иначе или не реализована — проверить разработчику.
- Воспроизведения **одного хода** с середины: нужен снимок состояния до хода + фрагмент журнала этого хода + входная фраза.
  Сейчас replay только с создания мира.
- `import` — ни команды, ни роли модели, ни записи пака.
- Создания героя на лету — ни ИИ-пути, ни пошагового режима, ни хранения мотива/средств/возможностей героя.

### Противоречия и дыры
1. Критерий покрывает 2 из 5 подзадач. Для import, героя на лету и предыстории проверяемого критерия нет. → В1.
2. «Ход из репорта воспроизводится» vs текущий replay «только с начала мира». Нужен снимок до хода; ТЗ 9 говорит «снимок
   состояния», но не уточняет — до хода или после. → В3.
3. Отказ (`refusal`) — ход откатан. Что воспроизводить: откатанный ход до отказа. Это возможно только если снимок — до хода. → В3.
4. «Последние N ходов» — N не задан. «Сырой запрос/ответ» — один последний вызов или все вызовы хода (рассказчик + world +
   повторы). Блобы журнала — копировать в репорт или ссылаться. → В2.

6. Авто-метки: файл на каждую метку? `limit-exceeded` может быть частым — десятки файлов за сессию. → В4.
7. `invalid-defeat` и `context_overflow` — метки вне списка ТЗ 9. Писать файл или нет. → В4.
8. Живые миры пользователя: `issues/` внутри `saves/<world>/` или в корне игры — ТЗ пишет «в `issues/`». Снимок состояния
