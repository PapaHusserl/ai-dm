# Ревью партии 0 (цена экземпляра) — мама-кабан, 2026-10-07

Объём: незакоммиченный `git diff src/` + правки тестов, план `docs/CUSTOM-ITEMS-PLAN.md` раздел 8 и «Ответы проектировщика».
Прогон: `uv run pytest` — 22 failed / 8632 passed; все падения в `tests/unit/persistence/` (старые тесты ждут v5 или
вызывают `migrate` без context); их сейчас дописывает kaban-doeba. `ruff check src` чистый.

## Хорошо
- `InventoryEntry.cost_cp` (обязательный) + `quality`, `GroundItem.cost_cp/quality` сделаны как в плане; стек =
  `(item_id, cost_cp, quality)` в `add_item`.
- `remove_item`: без цены снимает с самого дешёвого стека (В22), с ценой снимает точечно, возвращает снятые записи;
  слоты equipped очищаются только когда этого id больше нет совсем.
- `count_item` теперь суммирует по стекам; `item_totals` используется в бою (`special_ammo`, `item_options`), так что
  при двух стеках не будет двух одинаковых кнопок `use_item:<id>`.
- disarm: у героя снимается самый дорогой стек (надетый), цена и качество идут на землю, в `take` и в
  `settle_ground`. Цепочка «выбили → лежит на земле → подобрали/досталось после боя» цену сохраняет.
- «Получено» (`loot_snapshot`/`gains_lines`) считается по ключу `(item_id, cost_cp, quality)`, две строки одного id
  больше не перетирают друг друга.
- `MigrationContext` в виде dataclass с dict цен; m0006 не импортирует модели; неизвестный id получает 0 и строку в отчёте; `quality` не ставится.
- Порядок в `ui/cli.py`: сначала реестр, потом сейв. Вынос в `campaign_registry` убрал дублирование.

## Замечания (по важности)

### Важные
1. **`peek_campaign_id` читает manifest раньше, чем `recover_slots`** — `persistence/store.py::peek_campaign_id`,
   `ui/cli.py::prepare`. Если запись слота прервалась (manifest лежит в `.tmp-*`/`old`), `load_slot` бы его
   восстановил, а peek падает с FileNotFoundError, и игрок видит «Нет автосохранения». Предлагаю вызывать
   `recover_slots(root, world_id)` в начале `peek_campaign_id` (или прямо перед peek в `prepare`).
2. **Реестр в cli берётся по campaign_id из manifest до миграции, а после загрузки не сверяется** — `ui/cli.py::prepare`.
   m0003 проставляет `campaign_id="vale"` при миграции, поэтому у v0–v2 сейвов peek возвращает None. Сейчас это не
   ломается, потому что у vale нет `content/`, но `registry` и `pack_dir` остаются от None, а `campaign_id` уже
   берётся из `bundle.world.campaign_id`. Предлагаю после загрузки так: если `bundle.world.campaign_id != campaign_id`
   из peek, пересобрать `pack_dir, registry = campaign_registry(...)`. Это одна проверка, зато пак и реестр
   гарантированно совпадут.
3. **Отчёт миграции нигде не показывается** — `store.py::load_slot` / `game/app.py::load` / `cli.py`. В плане сказано
   «неизвестный id → cost_cp=0 + запись в отчёт миграции», но `context.report` после загрузки никто не читает (а
   контекст, который строится внутри `load_slot`, вообще недоступен снаружи). Предлагаю хотя бы
   `say(notes, ...)` в cli и строки в ответе `GameApp.load`, если `context.report` не пустой. Без этого предметы с
   ценой 0 появятся молча.
4. **Запасной вариант `load_slot` без контекста (встроенный реестр)** — `store.py::load_slot`. Оба реальных вызова
   (`cli.prepare`, `GameApp.load`) передают пакетный реестр, поэтому в игре цены паковых предметов правильные.
   Риск в будущих вызовах (инструменты, тесты, партия А): у предметов `drunk_dragon/content` молча станет
   `cost_cp=0`, ведь отчёт теряется (п. 3). Кроме того, `persistence` теперь импортирует `content.loader`, что
   нарушает слой, который сам план и защищал («m0006 получает только dict цен»). Предлагаю убрать запасной вариант
   и сделать `context` обязательным при `version < current_version` (уже есть `MigrationContextRequired`), а тестам
   передавать `MigrationContext.from_registry(load_registry())` явно. Если оставлять, то хотя бы добавить строку в
   `context.report`: «цены из встроенного реестра».
5. **`remove_item(cost_cp=...)` не учитывает quality** — `rules/inventory.py::remove_item`, `combat/defeat.py::do_rob`.
   Стек определяется тройкой `(item_id, cost_cp, quality)`, а точечное снятие идёт только по паре `(id, cost)`. В
   партии 0 качества ещё нет, но в партии В появятся трофеи с качеством. При совпадении цены у двух стеков, например
   «поношенный» по ПО и SRD с той же ценой, `pick_valuables` вернёт одну запись, а снимется другая (сначала
   дешёвая сортировка, при равной цене первая по порядку). Предлагаю добавить `quality=...` в `remove_item` (по
   аналогии с cost_cp: None — любой) и передавать его из `do_rob`. Сейчас это дешевле, чем потом в партии В.

### Средние
6. **`pick_valuables` всё ещё кидает InventoryError на неизвестный id** — `rules/inventory.py::pick_valuables`. Цена
   теперь берётся из записи, реестр в функции нужен только ради этой проверки. В тестах плана (партия А) записано:
   «неизвестный id пропускается без исключения». Как отклонение партии 0 это допустимо, раз поведение не менялось.
   Но в партии А кастомный id без overlay сломает грабёж (`do_rob` упадёт). Пометить в HANDOFF/плане как
   обязательный пункт партии А, а лучше просто удалить проверку уже сейчас: она больше ничего не защищает.
7. **Звезда «надето» в `/inv` при равной цене** — `game/sheet_text.py::inv_lines`. `is_worn` = `cost_cp ==
   dearest_cost`: если у двух стеков одна цена и разное качество, звёздочки получат оба. Пока качества нет, это не
   проявится. Для партии В достаточно отмечать только первый стек с максимальной ценой (флаг «уже отметили» по id).
8. **Цена выбитого у монстра = SRD** — `combat/disarm.py::strip_weapon`. По плану здесь нужна «цена трофея по ПО»,
   kaban сознательно отложил это на партию В. Приемлемо: GroundItem уже несёт цену, в партии В поменяется одна
   строка. Нужен TODO/пункт в плане партии В: «`strip_weapon` монстра → `trophy_cost`», иначе забудется, и выбитое
   оружие рядового врага останется дороже трофея с его тела (это противоречит решению по балансу).
9. **`WITH_CONTEXT = {5}` завязан на номер версии, а не на конкретную функцию** — `persistence/migrations/__init__.py::migrate`.
   Если в тестах подменить цепочку (`registry=`) и положить на ключ 5 свою функцию с одним аргументом, вызов
   сломается. Проще по-джуновски: передавать context всем миграциям (`fn(data, context)`, старые принимают
   `context=None` и игнорируют) или проверять `fn is migrate_v5_to_v6`. Не блокер.

### Мелкие и стиль
10. Модель `PackItem` для паков — отклонение разумное: в YAML пака цены нет, она берётся из реестра при сборке через
    `add_catalog_item`. Других вариантов не вижу. Оставить.
11. Качество в скобках, «Скимитар (поношенное)»: в плане префикс («поношенный скимитар»), но с прилагательным
    пришлось бы согласовывать род («поношенный/поношенная/поношенное»). Суффикс в скобках проще и корректен для
    любого рода. Принять, но обновить план (раздел 8, `entry_name`) и golden `/inv` в партии Б. Слово «б/у» для `used` в
    скобках читается нормально.
12. `combat/available.py::item_options` — тернарник `note = ... if ... else ...` заменил явный if/else. Это
    постороннее переформатирование, не нужное для задачи (CLAUDE.md просит не трогать лишнее). Вернуть if/else.
13. `migrate_v5_to_v6` не трогает `world.npcs` и компаньонов. Проверил: инвентарь в state есть только у `HeroState`,
    так что это корректно. `LastCombat.gear` появится в партии А и сразу должна писаться с cost_cp (миграция той
    же v6). Это совместимо, потому что m0006 через `fill` пропускает записи, где `cost_cp` уже есть.

## Совместимость v6 с партиями А/Б/В
- Одна версия v6 (В23): m0006 можно дополнять в партиях А и В (`world.custom_items`, `last_combat.gear`), функция
  идемпотентна по `cost_cp`. Важно не выпускать релиз между партиями 0 и В: иначе пользовательские сейвы уже будут v6
  без полей А и B, и для этого понадобятся default-значения в моделях. Зафиксировать в HANDOFF.
- Для overlay партии А нужно, чтобы `MigrationContext.from_registry` получал реестр **с** overlay кастомных, но
  overlay живёт в самом сейве. Кастомные id в v5-сейвах не бывает, так что проблемы нет. Для новых v6-сейвов цена
  уже в записи.
